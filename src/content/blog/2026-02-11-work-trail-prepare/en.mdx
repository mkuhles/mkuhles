## Installation and the first commit

The first steps are setting up the project with `ddev`:

```bash
mkdir cars && cd cars
ddev config --project-type=drupal11 --docroot=web
ddev start
ddev composer create-project "drupal/recommended-project:^11"
ddev launch
```

After that, the Drupal installer shows up in the browser.

<PostImage src={install} alt="Screenshot of the drupal installscreen (Choose language)" />

According to the task description I should install `drush`. It’s basically indispensable if you want to work efficiently with Drupal.

```bash
ddev composer require drush/drush
```

For example, with `drush` we can skip the browser-based installation — there’s a shortcut:

```bash
ddev drush site:install --account-name=admin --account-pass=admin -y
```

Now just run `ddev launch $(ddev drush uli)` and you’ll be logged into your local Drupal 11 installation as Admin. Don’t worry: `uli` doesn’t mean “Uli” — it stands for “user login” and generates a one-time login link.

Next: exporting configuration. We haven’t configured anything yet, but the task repeatedly mentions committing — so we commit the initial state.
Now we need our IDE. I start VSCode directly in the project directory:

```bash
code .
```

In `web/sites/default/settings.php` we look for `config_sync_directory` and set our config directory to `../config/sync` as required. The important part is that the directory is outside the webroot — otherwise configuration could end up being reachable through the web (depending on your setup), and nobody wants that.

Now we can export the first time:

```bash
➜  cars: ddev drush cex
 [success] Configuration successfully exported to ../config/sync.
../config/sync
➜  cars: find config/sync -type f | wc -l
178
```

A lot for “doing nothing”, right? Drupal exports *all* configuration so you can reproduce the exact state of one Drupal instance on another. `drupal/recommended-project` already comes with quite a bit of default configuration (blocks, views, the Article and Page content types).

Next step: the first commit. I assume you know how to use Git — IDEs can do a lot of it for you.
But the important part is: don’t just commit everything. I version neither `vendor/` nor `web/core/`, because both are fully reproducible via `composer.lock` and would just bloat the repo. So they go into `.gitignore`. IDE files also have no place in the repository.

There are also secrets in the directory tree. Normally I set up the repo so I have a local settings file containing secrets and environment-specific settings. I then import that from the general `settings.php` (`web/sites/default/settings.php`). This way the general `settings.php` can be versioned. Since I’m not going live here, and `ddev` already puts its configuration into an ignored file, I don’t need to do more right now.

My `.gitignore` ends up looking like this:

```
/vendor/
/.vscode/
/.idea/
/.ddev/

/web/sites/*/files
/web/sites/*/public
/web/sites/*/private

/web/core/
```

You can also use `web/example.gitignore` from `drupal/recommended-project`.

Now it’s only 206 files instead of originally over 10,000.

In a real project the build would happen via CI (`composer install --no-dev --optimize-autoloader`).

I then add the `.routing.yml` — similar to Symfony, it’s just routing configuration:

```yml
vehicle_checker.detail:
  path: '/vehicle-check/{node}'
  defaults: 
    _controller: '\Drupal\vehicle_checker\Controller\VehicleCheckerController::detail' 
    _title: 'Vehicle Checker'
  requirements: 
    _permission: 'access content'
  options:
    parameters:
      node:
        type: entity:node
```

By using a parameter converter (`entity:node`) I avoid manual loading and automatically get access control and cache metadata.

## Implement the controller

Because the route parameter `{node}` is typed as `entity:node`, the controller receives a node object directly.

File:
`web/modules/custom/vehicle_checker/src/Controller/VehicleCheckerController.php`

```php
<?php

namespace Drupal\vehicle_checker\Controller;

use Drupal\Core\Controller\ControllerBase;
use Drupal\node\NodeInterface;
use Symfony\Component\HttpKernel\Exception\NotFoundHttpException;

class VehicleCheckerController extends ControllerBase {

  public function detail(NodeInterface $node) {

    // Safety: Only for the correct content type.
    if ($node->bundle() !== 'cars') {
      throw new NotFoundHttpException();
    }

    // Read field (adjust machine name if needed).
    $release_date = $node->get('field_release_date')->value;

    if ($release_date) {
      $year = date('Y', strtotime($release_date));

      // If release year is 2020 → 404
      if ($year === '2020') {
        throw new NotFoundHttpException();
      }
    }

    return [
      '#theme' => 'vehicle_checker_detail',
      '#node' => $node,
      '#cache' => [
        'contexts' => ['route'],
        'tags' => $node->getCacheTags(),
      ],
    ];
  }

}
```

Important:

* `bundle()` must match your content type machine name (`cars` or `vehicle` — depending on what you created).
* Adjust `field_release_date` if needed.
* By passing the node cache tags, the page is automatically invalidated when the vehicle is updated.

## Twig template for the output

So we don’t just return `#markup`, we add a small Twig template.

File:
`web/modules/custom/vehicle_checker/templates/vehicle-checker-detail.html.twig`

```twig
<article class="vehicle-checker-detail">
  <h1>{{ node.label }}</h1>

  <p><strong>Price:</strong>
    {{ node.field_price.value|number_format(2, ',', '.') }} €
  </p>

  <p><strong>Release date:</strong>
    {{ node.field_release_date.value|date("d.m.Y") }}
  </p>

  {% if node.field_brand.entity %}
    <p><strong>Brand:</strong>
      {{ node.field_brand.entity.label }}
    </p>
  {% endif %}
</article>
```

## Register the theme hook

So Drupal knows which template belongs to `vehicle_checker_detail`, I add this in `vehicle_checker.module`:

```php
<?php

/**
 * Implements hook_theme().
 */
function vehicle_checker_theme($existing, $type, $theme, $path) {
  return [
    'vehicle_checker_detail' => [
      'variables' => [
        'node' => NULL,
      ],
      'template' => 'vehicle-checker-detail',
    ],
  ];
}
```

## Move the module

I noticed that I initially created the module in the wrong folder. It currently sits directly under `web/modules`. I’m going to move it — but be careful: you can’t just do that if the module has already been installed and the routes have been hit.

```bash
ddev drush pm:uninstall vehicle_checker -y
mv web/modules/vehicle_checker web/modules/custom
ddev drush en vehicle_checker
ddev drush cr

# If Drupal still can’t find the route:
ddev stop && ddev start
ddev drush cr
```

Most of the time, `drush cr` is enough for Drupal to pick up routes again. If not: restart the containers.

## Conclusion

As practice for a trial day, this is pretty realistic.
It demonstrates:

* a clean setup with DDEV + Composer
* structured work with config exports
* site building (content type, taxonomy, views)
* theming (subtheme + Twig overrides)
* backend understanding (routing, controller, 404 logic, cache)

In a real project I would:

* not hardcode business rules (“2020”) but make them configurable
* add tests (a kernel test for the 404 logic)
* potentially implement the route logic via an access check instead of throwing an exception

This is doable in four hours — assuming you’ve run through the Drupal workflows a couple of times before.

And honestly: doing a complete end-to-end run from installation to custom module once takes a lot of pressure off before a trial day.
